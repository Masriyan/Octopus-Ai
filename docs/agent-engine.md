# 🤖 Agent Engine

The heart of Octopus: how a message becomes a plan, tool calls, and a final answer. All in `backend/agent.py`.

> 📎 Related: [Architecture](architecture.md) · [Providers & Models](providers-and-models.md) · [Tools Reference](tools-reference.md)

---

## Entry point

```python
async def process_message(self, conv_id, user_message, cancel_event=None):
    # yields: text / tool_start / tool_result / plan / error / done
```

It's an **async generator**. The WebSocket handler in `main.py` runs it as a background task and forwards each yielded event to the browser, while listening for a `stop` frame that sets `cancel_event`.

---

## The turn, step by step

1. **Save** the user message (`memory.add_message`).
2. **Build context** (`_build_messages`): system prompt + reconstructed history (see [History](#history)).
3. **Inject memory** (`_retrieve_memories`): RAG search on a threadpool; relevant hits (score ≥ 0.35) added as a `<memory>` system note.
4. **Resolve provider** (`get_provider`). On config error → emit `error` + return.
5. **Decide tool mode** from `tool_mode` + `provider.supports_native_tools`:
   - `none` → plain streaming, no tools
   - `native` → the native loop with function-calling
   - `emulated` → the prompt-based loop
6. **Run the loop** (below).
7. **Save** the final assistant text and emit `done`.

---

## Native loop

Up to **10 iterations**:

```text
repeat:
    stream model → collect text (yielded live) + tool_calls
    if cancelled: stop
    if no tool_calls: this is the final answer → break
    append a canonical assistant message carrying tool_calls
    persist that assistant tool-call turn
    for each call: emit tool_start
    run all calls concurrently (asyncio.gather)   ← the "swarm"
    for each result:
        emit tool_result   (+ emit "plan" if the tool was update_plan)
        append a canonical tool message (id + name + content)
        persist the result
    if any failed: append a [Self-Healing] system note (retry guidance)
```

- **Parallelism** — independent tool calls in one turn execute together.
- **Self-healing** — failures don't end the turn; the model gets a `<tool_failure>` note (treated as untrusted) and can adjust arguments or switch tools.
- **Ids** are generated by the agent so a call and its result always match across providers.

## Emulated tool calling

For models without native function-calling (selected when `tool_mode` is `emulated`, or `auto` + unsupported). Implemented by `_run_emulated`, `_build_emulation_prompt`, `_parse_action`.

The agent injects a protocol describing the tools and asks the model to emit:

````text
```action
{"tool": "<name>", "arguments": { … }}
```
````

Loop (up to **8** steps):
1. Buffer the model's full reply (so the action JSON isn't shown to the user).
2. `_parse_action` extracts a tool call (handles fenced blocks **and** bare/nested JSON).
3. **No action** → it's the final answer; stream it out, persist, stop.
4. **Action** → emit `tool_start`, run the tool, emit `tool_result` (+ `plan`), append an `<observation>` (untrusted) and loop.

This is what makes even tiny local models tool-capable.

## History

`_build_messages` reconstructs the context from persisted messages — but **does not** replay the raw tool-call protocol from disk. Replaying ids across an assistant `tool_calls` turn and each tool result, for every provider, is fragile. Instead:

- `user` → `user`
- `assistant` (with past `tool_calls`) → assistant text + a short note like `[called \`file_operations\` with {…}]`
- `tool` result → a `user` message wrapped as `<tool_result tool="…">…</tool_result>` (truncated, untrusted)

The **precise** function-call protocol is only used for the **current** turn, where ids are under the agent's control. This fixes cross-provider reload bugs while keeping useful context.

## Canonical message format

The agent always works in **OpenAI chat format**; each provider serializes it (see [Architecture §4](architecture.md#4-message-format-the-canonical-wire-model)). Tool messages carry `tool_call_id` **and** `name`, which is what lets Anthropic/Gemini/Ollama reconstruct their native shapes correctly.

## Memory integration

| Layer | What | Where |
| :-- | :-- | :-- |
| Short-term | last `max_context_messages` of the conversation | `memory.py` (JSON files) |
| Long-term | semantic recall across all past chats | `vector_memory.py` (Qdrant + embeddings) |

Embeddings are written on a background threadpool and serialized by a lock (the HF tokenizer isn't thread-safe). RAG retrieval runs via `asyncio.to_thread` so it never blocks streaming. If the vector stack isn't installed, both quietly no-op.

## Planning & delegation

- **`update_plan`** is a normal tool, but the agent gives it special UI treatment: whenever it succeeds, the agent emits a `plan` event so the front-end renders a live checklist. The model is encouraged (by `SYSTEM_PROMPT`) to plan first for non-trivial tasks.
- **`delegate_task`** runs a *nested* mini agent loop (in `delegate_tool.py`) with all tools except delegation, returning a summary. This keeps the main thread focused and enables optional per-subtask model routing.

## Event types (yielded by `process_message`)

| Event | Shape | Meaning |
| :-- | :-- | :-- |
| `text` | `{type, content}` | a streamed token chunk |
| `tool_start` | `{type, tool, arguments, id}` | a tool is about to run |
| `tool_result` | `{type, tool, result, id}` | a tool finished |
| `plan` | `{type, steps:[{title,status}]}` | the live plan changed |
| `error` | `{type, content}` | a recoverable error message |
| `done` | `{type, content}` | the turn finished |

These map 1:1 to what the WebSocket sends; see [API Reference](api-reference.md#websocket-protocol).

## Tuning knobs

| Behavior | Where |
| :-- | :-- |
| Max native iterations (10) / emulated steps (8) / delegate steps (5) | constants in `agent.py` / `delegate_tool.py` |
| Personality & policy | `SYSTEM_PROMPT` (or per-user `system_prompt` config) |
| Context size | `max_context_messages` |
| RAG threshold (0.35) / top-k (3) | `_retrieve_memories` |
| Creativity | `temperature` |
